# 19 天共学总结：我现在怎么看 Agent

记录日期：2026 年 10 月 26 日。Task 0–5 已完成；这篇先按已经做过的实验写，结营前如果又有新体会再补。

刚开始学的时候，我把 Agent 想成“接上大模型，再给它几个按钮”。后来从 Chapter 1 一路做到多 Agent，发现这想法太简单了。模型会说下一步该做什么，不代表事情真的做成了。它需要看对上下文，调用合适的工具，还得把工具返回的东西读进去，最后接受结果检查。现在我更愿意把 Agent 看成一个会循环工作的系统，而不是一段写得很漂亮的提示词。

Task 0 的联网搜索给我上了第一课。离线演示里 ReAct 轨迹很顺，但我第一次用 Kimi 真搜时，三轮都在继续调用搜索，到了迭代上限也没有答案。后来把上限调到八轮，模型实际搜完并给出了最终回答。我当时才分清“工具调用成功”和“任务完成”是两回事。看日志时也不能只盯着最后一句成功或失败，要看每一步工具有没有返回、模型为什么又搜了一次，以及最终有没有真正回答问题。

Task 1 学上下文工程，我最深的印象不是压缩率 2.7%，而是压短以后不能把重要条件弄丢。Prompt 是指令的一部分，Context 还包括历史对话、工具结果、任务进度和拿来回答问题的资料。材料很多时，往窗口里全塞进去并不一定更好。这次上下文感知压缩实验跑了七轮、十五次工具调用，没有溢出，但我也不敢只凭压缩率就说答案一定更可靠，还是要回头看保留了哪些依据。

Task 2 把“记忆”和“知识库”分开了。用户记忆实验里，我先让一个虚构用户留下偏好，再把代码语言偏好从 Python 改成 JavaScript，换个进程重新提问，它仍能读到更新后的内容。这比看到一行“保存成功”更有说服力。BM25 检索则给了我反面例子：搜 `model distillation` 能命中，换成 `cat` 却漏掉相关文档。关键词检索在精确术语上很有用，但不能指望它自动理解每个同义说法。记忆主要管“这个人现在有什么稳定信息”，知识库主要管“资料里有什么可引用的内容”，两者都需要更新和核对。

Task 3 做执行工具时，我故意试了语法错误、越界路径、超时和长输出。最提醒我的是官方演示中途有检查失败，但进程仍以零退出；光看退出码根本不够。工具描述和参数要清楚，执行边界也要明确。模型可以提议写文件或运行命令，真正动手的工具服务还要做校验，并把失败原因如实返回。我这次也连了 MCP Client 和官方 Server，感受到标准接口的价值，不过测试脚本按预设顺序调用工具，不等于模型已经学会自主选工具。

Task 4 的代码辅助数学实验，程序给纯推理 8/11、代码辅助 11/11。后来查看原始记录才发现，纯推理有三题的可见回答被输出长度截断了，不是已经证明它算错。我现在看到一个分数，会先问：题目是什么、判分口径是什么、接口有没有截断？跑代码也是一样，写出来只是中间步骤，执行、观察反馈和核对真值才算走完一轮。这次只跑了官方 11 道教学题，没有把它写成 30 道正式评测通过。

Task 5 的四章翻译示例让我第一次直观看到多 Agent 的好处和代价。Manager 管计划和文件索引，Glossary 整理术语，Translation 分章翻译，Proofreading 提问题并让部分章节返工。共享术语表让指定译法更统一；但四 Agent 总共用了 24,211 tokens，单 Agent 对照只用了 7,080。以后遇到短小、步骤少的任务，我不会为了“看起来高级”就拆成好几个 Agent；只有任务确实能分工、交接规则说得清楚、质量收益值得额外成本时，我才会考虑多 Agent。

回头看这段共学，我最大的变化是开始追问证据。截图、工具记录、实际生成的文件、模型响应状态和评测口径，都比一句“跑通了”更重要。接下来我想做一个规模很小、问题明确的 Agent：先选一个自己真的会用的场景，再规定输入、工具权限和验收标准，跑起来以后记录失败在哪里。这样做起来慢一点，但我更有把握知道它到底帮了什么忙。
